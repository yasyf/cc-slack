## [Unreleased]

### Changed

- "Got it, back in a minute." posts only while the session holding your DM compacts itself, never while one of its background agents does. Claude Code runs the session's `PreCompact` hook for every agent's compaction with nothing naming the agent, so the hook now reads the session's transcript and the daemon marks the session compacting only when its context stands at 90% or more of its compaction point: the `preTokens` of its last auto `compact_boundary` record, capped by the window Claude Code resolves from `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `modelSettings.<model>.autoCompactWindow` or `autoCompactWindow`. A manual `/compact` always marks. The mark ends when the transcript records the compaction or the process starts again, no longer when an agent's finished compaction runs `SessionStart`. Before, each agent's compaction marked the session, and the 8-second check could not clear the mark while the session sat in one long tool call: on Nov 11 at 11:05 and 11:09 AM you got the ack while an agent compacted and the session's context stood at 358,273 and 366,264 tokens against its 567,047-token point, and you wrote "You're compacting every 5 mins based on these responses look into that it's a bug of some kind".
- The daemon reads GitHub through ccx's GitHub gateway, `ccx vcs gh -- api graphql` with `GH_REPO` and `CCX_CALLER=cc-slack`, for the live PR state its cards poll each minute, the PRs a post links, and a card's PR descriptions, which it also serves from ccx's cache for 10 minutes. Before, it POSTed `api.github.com/graphql` itself with the `gh auth token` user token, outside ccx's ledger and rate-limit floor, and read GitHub's `RATE_LIMIT` error type as `RATE_LIMITED`, so it never saw the limit. A read that fails draws each PR it asked about from the daemon's last answer for it: a post still links a PR it linked before, and a card keeps its PR's last state. A read now goes out once per repository, so a GitHub App installation token reads each repo the app holds.
- A thread or history read gives a message drawn as blocks its words once, with each `data_table` row by row and each chart's title: a question card, and a card linked into a thread under `shares`, read as its header, body, Show me table and options. Before, the read put the card's notification text, its title and body joined by " — ", above the blocks that draw the same words, so the body read twice, and it skipped data tables, so a Show me before-and-after table never reached the session. A notification text keeps each line or " — " piece its blocks leave out, such as an alert's title. A card's notification text now writes its body's markdown links and bold the way the card draws them, so a notification shows `The fix` linked instead of `[The fix](https://…)`.
- A tap or Undo on a question card goes to the `card_command` before it reaches the session, and when the program takes it the session's `slack.action` carries `recorded: true` and no `capture`, with a directive saying the program already posted the one record the asking lane reads, so post no record or capture of it. Before, the session got the tap first with a directive to hand the answer to the lane that asked and capture it, and the program then recorded it too, so each answer reached the asking lane twice. A program that exits non-zero, or a card it does not know, leaves the old directive and capture with the session.
- A withdrawn PR tap card comes back in place when the card command draws it again under the waits id it was withdrawn from: through a post naming its PR in `tap_prs`, `redraw-pr-cards --pr` or a new head of its PR, the same message gets its Approve and Hold back, its withdrawn line and reaction go, and nothing new posts. Before, it stayed withdrawn and the next post naming the PR drew a second card at the DM root, so on Nov 11 two tap cards a drive withdrew while their PRs waited on a release could only come back as new posts. A card drawn again under that waits id with a PR's changed line it did not carry posts fresh where a first ask lands instead, and the withdrawn card says Replaced: with that line and links the new one, as an answered card does, so a card a drive withdrew while its PR was reworked to your words asks again below your latest messages and says what changed. A card drawn with no waits id or another stays withdrawn, and a note card pulled before you answered is still never drawn again.
- A waiting card asked again under its `waits` id with new words posts the new version as the live card where a first ask would land, and the old card is edited in place to the new words, its buttons replaced by a line, Asked again with new words, linking the new card. Each older copy of it reads that line too, so one card stays answerable. The `dm-status` reply names the new card. Before, the card was only edited in place, so a reworded question never reached the place you were reading, though on Nov 6 you wrote "Replace in place but also send here just to be clear". The same words still post nothing, and a card with `in_place` set, the same question drawn again such as a drive's line saying it is being redone, is edited where it sits and posts nothing.
- A session holding your DM that posted a drive's card is told, for each message of yours, to ack it in one sentence and then start a handler that acts on it. Before, it was told to act on it, so the drive's communicator did the work itself instead of handing it off.
- `cc-slack check-post` reads the words of each link, `<url|words>`, as the reader sees them, for drive words, one-letter codenames, internal ids and ULIDs, zone labels, options named by number and unwrapped identifiers. Before, it skipped every link whole, so words such as "the lane" or "option 2" passed under a link. A linked commit sha, PR number or build number still passes.
- A post to your DM that links more than five Slack messages or alerts goes out as pages, each cut at the last blank line before the line holding its sixth link, so every card it links draws under it. Before, Slack drew the first five and showed the rest as bare words, so a post asking you to tap seven cards drew five: on Nov 11 you wrote "How many times do I have to tell you if you're telling me to tap something you need to include the unfurled card here". A line linking six or more is refused, as is an edit in your DM linking six or more, and `cc-slack check-post` flags such a line as `links-past-five`.
- A post to your DM that says something waits on you draws the tap card of each PR it links, or is refused and sends nothing when a PR draws no card. Before, linking a PR excused such a post from linking a card, so it could ask you to tap with no card under it.
- Your reply in the thread of a drive's question card reaches the drive's session as your message again, with the eyes reaction and the working line on it, and the card keeps its buttons until you tap one or the session answers it with `slack_card_answer`. A bare option number still taps that option, and now gets the eyes reaction too. Before, from 0.19.97, cc-slack took any words you wrote under a waiting drive card as the card's written-in answer: it closed the card, drew an Undo button, sent no eyes, no working line and no message, so a question you asked under a card went unanswered and was recorded as your pick.
- `cc-slack card-reopen --card <permalink> --reply <permalink>` reopens a card closed on your reply in its thread when that reply answered nothing: the card offers its options again, loses its check mark, the session hears the answer was never given, and the drive's card command records it as undone. It refuses unless the card shows that reply's words as its answer, so it never takes back a tap.
- A short DM line or reply holding a ```` ```chart ```` fence, such as a drive's `say` post with a chart, draws the chart as Slack's own chart. Before, a short text with no other markdown went out as plain text, so its chart showed as the spec's JSON.
- `cc-slack check-post` flags a line that reports no change, such as "No change since the last update." or "Nothing new.", and says to post nothing, or to react :+1: to a message that needs no answer. A line that says what changed, such as "No change to the API; the fix only touches the worker.", passes.
- `cc-slack check-post`'s wall-of-text fix no longer says to end with one direct question. A session whose questions go on cards read it as an order to ask in text; the fix now says only to keep each paragraph to three sentences and put steps and settings in a list.
- A ```` ```chart ```` fence in a card's body or a PR's Show me draws as Slack's own chart, a bar, line, area or pie, from the Vega-Lite spec it holds. `cc-slack card render` refuses a chart Slack cannot hold, such as a label past 20 characters, naming the label. Before, cc-slack showed such a fence as its JSON, so a drive drew each chart as a picture: on Nov 10 at 10:52 PM you wrote under one: "for the chart slack literally has the native version of this why didn't you build that for the renderer".
- Two to ten pictures in a row on a card draw side by side as one Slack carousel, each titled with its caption, so a question's pictures read as its options 1 and 2. A PR's pictures and a card's other pictures draw the same way. Before, each picture was its own full-width image, one under the next: at 10:55 PM you asked for them "gallery style labeled with each option (e.g 1, 2)".
- A table in a PR card's Show me draws as a Slack data table, as a table in a card's body does. Before, it drew as one line of text a row. At 11:01 PM you wrote "the two tables should be rendered in slack natively".
- A card linked in a post shows under the line even when another post linked it a few minutes earlier. Slack draws no link it showed in the same conversation within the past hour, so on Nov 10 at 11:51 PM two question cards linked 4 minutes after a post in another thread showed as plain links, and you wrote "those links should have been unfurled into their cards". Each Slack message link a post carries now goes out with a `post` parameter of its own, so Slack sees a link it has not shown and draws the card; the link still opens the same message.
- "Got it, back in a minute." posts only when the session's transcript shows your message missing. A session whose `PreCompact` hook named no transcript, as one started before v0.19.83 does, or whose transcript cannot be read, gets no ack. Before, such a session got the ack 8 seconds after each DM message whenever it or one of its agents compacted, busy or not.
- `slack_dm_status` with a `thread_ts` that is no thread in your DM, such as an order's thread in another channel, never posts at the DM root. A drive's question card still goes up at the root, once, with no link beside it and a `NO CARD LINK` warning; any other post naming such a thread is refused and sends nothing. Slack posts a reply under a thread it cannot find at the conversation's root, so before, the card's link landed at the DM root next to the card and drew it a second time: on Nov 10 at 10:36 PM two question cards that both named a thread in another channel each showed up twice in a row in your DM.
- "Got it, back in a minute." is back, only for a DM message from you that the session holding your DM has not taken in 8 seconds after it arrived while the session or one of its background agents compacts: cc-slack holds the ack, then looks for the message in the session's transcript and posts nothing when it is there. When it does post, the session gets `slack.message.acked` naming the ack, so it posts none of its own. A busy session reads your message within a second, as at 10:40 PM on Nov 10 when the ack landed in the same second the session logged the message, so it gets no ack; a session that really compacts gets its ack 8 seconds late.
- cc-slack no longer posts "Got it, back in a minute." under your DM messages while the session holding your DM, or one of its background agents, compacts. A background agent's compaction runs the session's PreCompact hook with nothing naming the agent, so each one marked the whole session compacting while it was mid-turn and reading your messages: on Nov 10 from 8:52 to 10:43 PM you got the ack eight times, four of them between 10:37 and 10:43 PM, and each of the four checked came while a background agent compacted and the session was mid-turn. A session that really compacts gets no ack until the next change brings one back only for a message the session has not picked up 8 seconds after it arrived.
- Your words in a channel steer a session only when they are to the bot: a message mentioning the bot, or one that mentions no one else and replies in a thread this machine's cc-slack posted in or starts a new top-level message. Those reach only the session holding your DM, on its DM watch with `relayed` set, when another session watches the channel whole, and a session watching one thread still gets them in that thread. Every other message you write there, such as a reply in a teammate's thread or a line that mentions a teammate, `@here` or a user group and not the bot, in any thread, reaches the sessions watching that channel or thread as Slack content, like a teammate's, without `operator`, so the Slack permission hook no longer counts it as an order delivered to the session. Before, every message you wrote in a watched channel arrived as operator steering: on Nov 10 from 4 to 10:12 PM a drive's coordinator got 23 of your messages from three team channels, and once those moved to the session holding your DM, five replies to a teammate in the teammate's own threads on Nov 11 from 9:30 to 9:31 AM, a joke and an emoji among them, each reached the drive's communicator as an order to ack and start a handler for.
- A card redrawn under its `waits` id edits that one card in place and posts nothing new. Each older copy of it loses its buttons and reads Redrawn in place with a link to the card, and no later redraw brings them back. Before, every redraw also posted a fresh copy, which since drive question cards moved to the DM root was a new top-level message in the DM, while the older copies kept working buttons: on Nov 10 between 8:17 and 8:33 PM one card had four live copies at the DM root.
- A card shows where a message mentions it by its permalink under words that name it, `<permalink|the lock card>`: the line reads as those words, Slack draws the card under them, in your DM too, and the post copies nothing, so the card stays one message. A post with `tap_prs`, a drive's question card and a post naming a PR in a thread each link the card in the thread under its question instead of posting a copy of its blocks, and an edit that links a message unfurls it as a post does. A post that shows a card's link as its raw URL, bare or labeled with its own URL, which Slack never previews, carries blocks copied from a card, or repeats an open card's title in your DM without its link outside the card's own thread is refused, naming the link to write; `cc-slack check-post` flags a raw DM link, and the bundled check-post flags any bare Slack message link. Before, links to cards in your DM never unfurled, and `send`, `reply` and `dm-status` posted a buttoned copy of each linked card under the post: on Nov 10 at 7:59 PM you wrote that messages were "still just pasting links and not expanding them", with card copies sent separately underneath, and at 9:02 PM a thread line linking five question cards put five copies in that thread. ### Added

- A release post in a channel whose feed you watch for releases also goes to `card_command` as `{"release": {"name", "line", "link"}}` each time its line changes, so a drive learns the turn a release one of its incidents named fails a step and reopens that incident's stop. Before, nothing went after a failed incident release until someone noticed: on Nov 10 the release carrying an incident's stop stuck at 9:36 PM and nobody went after it until 10:39 PM.
- A card's `body` line that holds only a markdown image, `![what it shows](/absolute/path.png)` or one drawn from an https url, shows that picture on the card where the line sits. The daemon uploads it to the `[pictures]` bucket as it does an artifact's picture, and a card redrawn in place keeps it without a second upload. `cc-slack card render` reads each such picture and refuses one it cannot read, one that is no PNG, JPEG, GIF or WebP image, one with no caption, and one named by a relative path. An image inside a sentence, a table cell or a code block stays text. Before, a body had no way to show a picture among its lines: on Nov 10 at 6:09 PM a question card about two dashboard layouts showed its screenshots as links only.

### Removed

- `card-copy` is gone, its op and its CLI verb: link the card's permalink under words that name it instead. A copy posted before still follows its card, and loses its buttons when the card is redrawn.

### Fixed

- A code block in a card's body escapes `&`, `<` and `>` as the card's other lines do, so `func of[T any](id string) <-chan T` shows whole. Before, the block went to Slack as written, and Slack read `<-chan T` as the start of a link or mention.
- `cc-slack check-post` reads no PR or build number inside a code span or a code block, since `send`, `reply` and `edit` link none there either: an id quoted from an error, such as `` `memory value #830225 out of bounds` ``, passes, and a bare #830225 in prose is still flagged. On Nov 11 a handler dropped such an id from an incident line because check-post told it to link a number that names no PR. Every rule that skips code spans, such as the unwrapped-identifier and drive-word rules, now skips code blocks too, and a one-line ```` ```echo hi``` ```` no longer hides the lines after it from the wall-of-text check.
- Each `--bg` session keeps its `cc-slack channel` server when another `--bg` session starts. Claude Code titles a `--bg` session process `claude bg-spare`, which cc-interact did not count as claude, so every `--bg` session under one `claude daemon run` resolved to the daemon as its window, and from 0.19.125 each new session's channel server made every earlier one exit: from 3:03 PM on Nov 11 all 13 drive handler sessions lost cc-slack's tools, Claude Code marking the exited server failed and never restarting it. The hook and CLI envelopes a `--bg` session sends now carry its own claude pid too, not the daemon's (cc-interact 0.42.1).
- A Claude Code window keeps one `cc-slack channel` stream: a channel server exits once a later-started one attaches for its window, and the daemon answers an earlier-started one with 409 Conflict. Before, a server a plugin reload left behind kept its stream, and with two or more `channel` streams in one window the agent-inject hook could not tell what the channel had pushed, so each linked Slack message and card tap reached the session twice: once as a channel tag and once from the hook. On Nov 11 the drive's communicator window held 17 such servers. A server built before this release stops streaming on the 409 but stays alive until its window exits (cc-interact 0.42.0).
- A PR in `tap_prs` that GitHub does not read, and that the daemon has no last answer for, still gets its card: cc-slack asks the `card_command` for it with no GitHub state, and the card command draws the card from what it holds. A post's reference that names one PR links the same way when the read fails; a bare number two listed repos could hold stays plain. Before, a PR the read left out, such as one GitHub answered `NOT_FOUND` for or one the daemon had never read before a rate-limited read, failed the call with `drew no card for tap_prs <PR>: cc-slack could not read it from GitHub`, so on Nov 11 the drive's PR cards stopped drawing while `gh pr view` still read the PR.
- The same text sent to two threads of one DM now posts in both. The permission hook's `once` ticket fingerprint now hashes the write's channel and thread along with its verb and text, so the second reply gets a ticket of its own. Before, every write in a DM spends at the person with no thread, so the fingerprint matched, the hook named the first reply's ticket again, and the daemon answered the second reply from that ticket's receipt with `replayed: true` and the first thread's permalink, posting nothing. A top-level DM post and a thread reply with the same text collided the same way, and so did `stream` in another person's DM.
- A DM post that says something waits on you goes out with each PR it links even when that PR's tap card does not draw, such as a card held while the PR waits on another job; the PRs that do draw still get their cards under it. Before, `dm-status` and `reply` refused the whole post with `drew no card for tap_prs <PR>: it waits on <job>`, so on Nov 11 a status answer had to drop two open PRs to post. A PR passed in `tap_prs` still refuses the post when its card does not draw.
- A Slack write with no explicit approval goes to Jev, which reads your own words, your Slack messages included, and your recorded rules, and decides; when it refuses, the refusal says Jev's reason. Before, three hard-coded checks refused such writes before Jev ever read your words. An order you sent the session counted for one write only, so the session's acknowledgement used it up and the handler's answer was refused. In a bug thread under the grant for one solved line, a post with a question mark or jargon, or any post once the bot had posted there, never reached Jev. An order linking another Slack place was dropped before Jev saw it. On Nov 11 that sent a question you asked in a bug-bash thread to your DM instead, and refused the answer again after you said "What the fuck why didn't you post this yourself". Your messages in the thread a write goes to now reach Jev too, and the limit of one solved line per bug thread is a rule Jev reads. An explicit approval still passes with no Jev call: a Yes you tapped or answered, your words linking the thread, a standing grant for the place, or an edit of the bot's own post.
- `slack_users` (`cc-slack users`) finds a person by user id through `users.info` and by exact email through `users.lookupByEmail`, so both still resolve while `users.list` fails, as it did on Nov 11 answering `fatal_error` on the bot and user tokens alike. A failure now names the Slack method and its error, such as `cc-slack can't look people up (Slack's users.list answered fatal_error)`, and points at `mcp__slack__slack_users_search`. Before, an id matched nobody, and a `users.list` failure read `cc-slack can't read this conversation (fatal_error)` and pointed at the thread and history tools.
- `slack_channels` (`cc-slack channels`) names `conversations.list` and its error when that call fails, and points at `mcp__slack__slack_list_conversations`, instead of saying it can't read a conversation.
- `slack_pickup` (`cc-slack pickup`) on a reply in a thread, called without `thread_ts`, puts the working line under the reply's thread. It reads the thread from Slack first. Before, it set the line under the reply's own ts, which Slack refuses, so the pickup failed after the eyes went on.
- A list of states that ends in "or waiting on you", such as "merged, open or waiting on you", no longer reads as a wait on you that needs a card. "Merged, open or waiting on you to pick a route", "The fix is open or waiting on you" and "Tests passed, release is open or waiting on you" still do: a state in the list is never a clause with its own "is".
- `cc-slack check-post` takes a repeatable `--asked`, a message of yours the post answers, word for word. A multi-agent term you used there, such as "the drive" in a question about the drive, passes in the answer. The message has to name the term as a whole word: "the drive" passes for "this drive" and "lane" for "lanes", but a question about the driver passes nothing. A post that answers no message naming the term is still flagged.
- A `send`, `reply` or `dm-status` cut by a daemon upgrade posts once. The CLI mints a request key for each of these writes, every Slack post the write makes carries that key and the post's step in its message metadata, and a call the daemon cut, `daemonkit: business session: context canceled`, is resent under the same key. The new daemon reads the channel or thread from the key's mint time, answers each step Slack already holds with that message, and posts only the rest. Before, the CLI gave up on a cut call, and the agent's retry posted a second copy of what the cut call had already posted, as one `dm-status` did at 2:16 AM on Nov 11.
- A card posted again into another card's thread, with new words or a new row, keeps the answers that thread holds. Before, the thread took the answers of the card's old thread in place of its own, so a card there you had answered took a second answer.
- An agent's second reply in a thread is no longer refused right after its first. Before, the agent's own reply became the thread's newest message, one it had never read, so every second reply waited on a fresh `slack_thread` read. A newer message from a person or another agent still needs a read, even when that agent posts as the same bot.
- The read-before-reply refusal says which check failed and the read that clears it: no read by this agent, a whole read past 10 minutes and how many messages it is behind the thread's newest, a truncated read, or a stale one. `cc-slack thread-seen` takes `--since` and counts the cached messages after it. Before, every refusal gave the same sentence.

- A post with `tap_prs` whose PR gets no card carries what the card command printed about that PR, such as that the PR is in no drive, instead of "the card command answered no card for it".

- With cc-present installed, a `dm-status` card that waits on an answer and did not come from cc-present is still posted, and the reply carries a `warning`: a question goes on the cc-present board first and reaches Slack through `cc-present send`.
- The permission hook's refusal prints the approval question as a cc-present board card for `cc-present ask -`, beside the Slack card for sessions without cc-present.
- An Explain more tap tells the session to answer with `cc-present reply` when the card is on a cc-present board, so the answer lands on both surfaces.

## [0.2.1] - 2026-10-23

### Changed

- One `dm-status` call posts a card from whatever it is given: text beside a card becomes its body, a missing status becomes `needs_you` on a waiting card and `info` otherwise, a missing title becomes the body's first line, and an option marked "(Recommended)" becomes the recommended answer. A card that still fails names every problem at once.
- An option label runs to 61 characters, so it fits a 75-character Slack button with "(Recommended)" after it.

## [0.2.0] - 2026-10-23

### Added
- A `waits` card names its recommended answer in `recommended`. The card shows that answer first as "<label> (Recommended)" in the primary style.
- Every `waits` card carries a built-in Other button beside Explain more. The backend opens a modal on the tap and pushes the typed text as a `cc-slack-card:wrote:<id>` action, which answers the card; the `slack.action` carries `other: true`. A bare Other tap answers nothing.
- `cc-slack card-answer --waits <id> --card <permalink>` answers a waiting card from another surface, such as a cc-present board. It fires the same `slack.action` capture a tap fires, naming the surface in `via`, and refuses a late answer by naming the one that won and whether it was written in.
- With `cc-present` on PATH, a posted `waits` card is added to the session's cc-present board, with each GitHub pull request in its `refs` as a live PR card, and an answer on Slack is sent there too. `dm-status --mirrored` posts a card the board already holds without telling the board again.
- `dm-status` returns the posted card's `ts` and `permalink`.
- `slack_dm_status` and `dm-status --about <waits id>` open a text reply with a Slack link back to that waiting card, including one another app posted in the session's status thread with an Explain more button for that id.

### Changed
- A `waits` card without `recommended`, with "(Recommended)" in a label, or with an Other option is refused.
- A card that reuses the `waits` id of a card still waiting edits that card in place instead of posting a second one. Reusing the id of an answered card is refused.
- The permission hook's approval card recommends Yes.
- The Explain more directive tells the session to reply with `about`, so the reply opens with a Slack link back to the card.
- A pull request in a card's `refs` is labeled "<repo> PR <number>".

## [0.1.10] - 2026-10-23

### Changed
- The permission hook asks about a Slack write the user did not request on an ask card in the DM status thread, never through `AskUserQuestion`. Its refusal prints the `slack_dm_status` card: the title names the place, the body carries the draft, and the answers are Yes and No. A tap on Yes approves the write.
- The plugin requires captain-hook 12.104.0 or later, which reads a tap on a cc-slack question card as the user's answer.
- A bare `slack-grant:<channel>` answer, or an asked answer to keep posting in a channel, now covers top-level posts there only. A reply in one of the channel's threads needs that thread's own `slack-grant:<channel>/<thread ts>` grant or another permission.
- The permission hook's owed-update rule is gone. A thread whose latest message is a person's, in a channel the session touched, no longer permits a reply there; a reply needs that thread's grant, a ticket, or the user's word. The daemon's thread read before an owed-update reply goes with it, and sends, replies, edits, and deletes no longer get the longer timeout that read needed.

### Added
- Each answer button on a `waits` card carries the card's options, and its `slack.action` payload carries them as `options`, so a reader can tell which answer the label is.

## [0.1.9] - 2026-10-23

### Added
- A `slack-grant:<channel>/<thread>` answer label grants writes in that one thread only, and `slack-revoke:<channel>/<thread>` withdraws it; an answer carrying a thread label for a channel no longer covers the rest of that channel.
- Two comms checks in the capt-hook pack run on every send, reply and edit wherever `[permissions]` is on: a post never asks a person for logs, versions, screenshots or recordings, and each line telling a person their problem is fixed cites the record of their case succeeding on the live build, their `usr_` id, and the thread owner.

## [0.1.8] - 2026-10-22

### Added
- The capt-hook pack carries the Slack write permission hook, its thread carry, and the plain-words warning, with scrubbed replay fixtures. A project opts in with `[permissions] enabled = true` in `.claude/cc-slack.toml`; `[[permissions.clis]]` names other posting CLIs the hook checks.

### Changed
- The daemon requires a ticket from sessions whose project sets `[permissions] enabled = true`, in place of the `permission_hook` file check. The `permission_hook` config key is gone.
- The plugin requires captain-hook 12.101.15 or later.

## [0.1.7] - 2026-10-22

### Added
- Ask cards carry a fixed Explain more button. Its tap reaches the session as `slack.action` with that label and the question id, asks for a fuller explanation in the thread, and leaves the question open.

### Changed
- A tap redraws the tapped card before the thread's root card.

## [0.1.6] - 2026-10-22

### Added
- `waits` on status cards: an ask card whose options are its only buttons, which says the asking lane is stopped until the tap, and whose `slack.action` carries the question id, the question, the answer, and a capture line for cc-notes.

## [0.1.5] - 2026-10-22

### Added
- Status cards carry `refs`, GitHub pull request and Buildkite build links whose live CI, queue, and landed state the daemon polls and redraws, plus `progress`, `started_at`, `eta`, `facts`, and a drive `rollup` of lanes and PRs.
- `asks` on status cards: buttons with stable ids, an optional confirm dialog and expiry, whose tap reaches the session as `slack.action` carrying the id.
- The root card keeps the last progress, facts, refs, links, and rollup any card set, lists every open ask, and shows a timeline of the last 5 updates.
- `dm-status --root-only` (`root_only`) redraws the root card without posting a reply.
- Optional `[github]` and `[buildkite]` config sections, each taking `token_env` or `token_command`.

## [0.1.4] - 2026-10-22

### Fixed
- Attachments in folders macOS protects from the daemon, such as `~/Documents`, post again. The CLI and channel server hand the daemon temporary copies, where before the daemon's open blocked until the request timed out.

## [0.1.3] - 2026-10-22

- The Homebrew cask strips the quarantine flag from the binary before its first run.

### Fixed
- The tagged plugin now carries its binrun descriptor, so installing the plugin at a release tag provisions the binary.
